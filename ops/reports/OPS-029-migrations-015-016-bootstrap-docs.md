## 결과

검증된 `001`~`014` 설치 기준에 migration `015`·`016`의 적용 순서와 안전 게이트를 추가했다. OPS-029 작성 당시 원본 작업 체크아웃에는 SQL이 `001`~`005`만 있었고, 검증된 통합 후보 브랜치 `codex/be-027-v2-review-queue-rpc`에 `001`~`016`이 있다는 차이를 모든 핵심 설치 문서에 명시했다. 이후 OPS-033 로컬 격리 통합 후보에는 `001`~`016`을 한 체크아웃으로 조립했다.

따라서 `006`~`016`이 승인된 통합 브랜치 또는 `main`의 한 체크아웃에 실제로 존재하기 전에는 운영 적용을 시작할 수 없다.

## 확정한 설치 계약

### 새 프로젝트

1. 새 빈 프로젝트에 `admin-schema.sql`을 한 번만 적용한다.
2. `001`·`002`를 중복 적용하지 않는다.
3. 한 체크아웃에 파일이 실제로 있는지 확인한 뒤 `003`부터 `016`까지 한 파일씩 순서대로 적용한다.

### 기존 프로젝트

1. `admin-schema.sql`을 다시 적용하지 않는다.
2. 적용 이력·핵심 객체·백업·주요 행 수를 먼저 확인한다.
3. 누락된 가장 이른 번호부터 한 파일씩 순서대로 적용한다.
4. 오류가 발생하면 다음 번호로 넘어가지 않는다.

### 015·016

- `015`는 `014` 뒤, `016`은 `015` 뒤에만 적용한다.
- `015` 적용 뒤 런타임 설정 4개를 모두 `false`로 유지한다.
  - `contribution_enabled`
  - `evidence_upload_enabled`
  - `public_projection_enabled`
  - `allow_exact_amount`
- `015`는 v2 Storage 버킷·정책·업로드 URL·서명 URL을 만들지 않는다.
- 실제 증빙 접수는 개인정보·이용약관·보유기간·악성 파일 검사·안전 미리보기 계약과 별도 승인이 끝날 때까지 시작하지 않는다.
- `016`의 `taran_list_review_queue_v2`는 `owner`·`admin`·`operations`의 AAL2 세션만 허용한다.
- `016`은 6개 비민감 필드만 한 번에 1~50건 반환한다.
- SQL 적용은 실제 업체 자료 접수·정확한 금액 저장·증빙 업로드·공개 반영·운영 배포 승인이 아니다.
